4월 킥오프 피칭 양식에는 제 역량을 적는 칸이 있었습니다. 웹 프런트엔드, LLM 스트리밍 UX와 함께 이렇게 적었습니다. "Claude Code 기반 AI 코딩 워크플로우로 기획 아이디어를 빠르게 시각적으로 검증."

두 달 뒤인 6월 22일, [The Traveling Soul](/projects/the-traveling-soul/)의 전시 화면 앱 `tablet-fe`에 첫 커밋을 남겼습니다. 커밋 메시지는 "Claude Code 하네스 설정 + pnpm 전환 및 초기 스캐폴딩"이었습니다. 화면 코드보다 먼저, AI가 이 저장소에서 어떻게 일할지를 정한 셈입니다.

그 뒤 10월 14일까지 커밋 551개가 쌓였고(549개가 제 것), 커밋한 날은 90일, TypeScript 코드는 약 4만 2천 줄이 됐습니다. 전시장 화면 다섯 개가 모두 이 앱 하나에서 나왔습니다. 이 글은 그 기간 동안 Claude Code와 일하는 방식을 어떻게 짰는지에 대한 이야기입니다. 질문은 하나입니다. **AI에게 무엇을 문서로 부탁하고, 무엇을 장치로 강제해야 하는가.**

먼저 밝혀 둘 것이 있습니다. 이 저장소는 커밋에 `Co-Authored-By`를 붙이지 않도록 설정했습니다. 그래서 커밋 기록만으로는 어느 코드를 Claude가 쓰고 어느 코드를 제가 썼는지 구분할 수 없습니다.

## 템플릿이 남긴 경고 아래에 원칙과 예외를 적었다

`tablet-fe`의 `AGENTS.md`를 열면 이런 블록이 먼저 나옵니다.

> This version has breaking changes — APIs, conventions, and file structure may all differ from your training data. Read the relevant guide in `node_modules/next/dist/docs/` before writing any code.

제가 쓴 문장은 아닙니다. Create Next App이 프로젝트를 만들 때 `BEGIN/END:nextjs-agent-rules` 마커로 감싸 넣어 두는 블록이고, "Initial commit from Create Next App" 커밋에 이미 들어 있었습니다. 다만 하는 말은 이 앱에도 그대로 맞습니다. 이 앱은 Next.js 16과 React 19로 만들었고, 모델이 학습한 Next.js와 실제로 설치된 Next.js는 다를 수 있습니다. 그러면 Claude는 그럴듯하지만 이 버전에서는 틀린 코드를 자신 있게 쓸 수 있습니다.

제가 한 일은 그 아래에 이 저장소만의 내용을 덧붙인 것입니다. 하네스 설정 커밋에서 이 앱이 무엇인지, 어떤 기술 스택을 쓰는지, 그리고 지켜야 할 경계를 적었습니다. 태블릿 앱은 게이트웨이를 거쳐서만 통신하고, 백엔드·로봇·MQTT 로직은 이 저장소에 없다는 원칙입니다. 그리고 바로 옆에, 전시장 데모에 한해서는 Next 서버가 MQTT에 직접 붙어 중계한다는 예외를 적어 두었습니다. 원칙과 예외가 한 문단에 나란히 있으니, Claude가 서버 쪽 MQTT 코드를 보고 원칙 위반으로 여겨 "고칠" 여지가 줄어듭니다. (이 예외를 만든 이유는 [2편](/blog/one-web-app-five-screens/)에 적었습니다.)

## 규칙은 필요한 만큼만 읽게 했다

닷새 뒤인 6월 27일, 한 덩어리였던 개발 규칙을 `.claude/rules/` 아래 파일로 나눴습니다.

```text
.claude/rules/
├─ general/      coding.md · typescript.md · prohibitions.md
├─ frontend/     nextjs.md · components.md · state-and-data.md
├─ backend/      server-bff.md
├─ reference/    codebase-map.md · orchestration-api.md
└─ workflow/     quality-gates.md
```

규칙 파일은 항상 불러오지 않습니다. 대신 `CLAUDE.md`에 작업별 표를 두고, "타입 설계나 zod 검증이면 `typescript.md`", "API 라우트나 SSE면 `server-bff.md`"처럼 지금 하는 일에 해당하는 파일만 골라 읽게 했습니다. 규칙이 많아질수록 모든 규칙을 매번 컨텍스트에 싣는 비용이 커지기 때문입니다. `CLAUDE.md`에도 "컨텍스트 절약을 위해 항상 로드되지는 않는다"고 적어 두었습니다.

같은 생각으로 코드를 찾는 순서도 정했습니다. grep을 하기 전에 코드베이스 지도(`codebase-map.md`)부터 봅니다. 폴더는 화면 조합 그대로 `components/<route>/<영역>/`으로 나눴기 때문에, 화면의 어느 자리인지 알면 폴더가 정해집니다. Figma 노드 id, `use<Name>` 형태의 store, `.z1-`로 시작하는 CSS 클래스처럼 이름 규약을 정해 두어 검색 한 번으로 위치를 찾게 했습니다. 서버와 주고받는 메시지 계약 문서는 1,400줄이 넘어서, 통째로 읽지 말고 해당 절만 찾아 읽으라고 적었습니다.

마지막 규칙이 가장 중요했습니다. 폴더나 store를 옮기면 **같은 커밋에서** 지도를 고칩니다. 지도가 코드와 어긋나는 순간, 지도를 먼저 보라는 규칙은 AI를 엉뚱한 곳으로 보내는 규칙이 되기 때문입니다.

## 부탁하는 규칙과 강제하는 규칙

규칙 문서를 아무리 잘 써도, 그것은 결국 부탁입니다. Claude는 대체로 따르지만 언제나 따른다는 보장은 없습니다. 그래서 `quality-gates.md` 첫 줄에 이렇게 적었습니다.

> 규칙은 "기대"가 아니라 "보장"이다 — 핵심 검사는 `.claude/settings.json` 훅으로 결정론적으로 강제된다.

파일을 편집할 때마다 훅이 그 파일에 prettier를 돌리고, JS/TS 파일이면 `eslint --fix`까지 실행합니다. 포맷과 린트는 Claude가 기억해야 할 일이 아니라 저절로 일어나는 일이 됐습니다.

핵심은 Claude가 턴을 끝내려는 순간에 걸리는 Stop 훅입니다. 읽기 쉽게 줄을 나누면 이렇습니다.

```bash
input=$(cat)
echo "$input" | jq -e '.stop_hook_active == true' >/dev/null 2>&1 && exit 0
cd "${CLAUDE_PROJECT_DIR:-.}" || exit 0
out=$(./node_modules/.bin/tsc --noEmit 2>&1)
[ $? -eq 0 ] && exit 0
{ echo 'tsc --noEmit 타입 오류 — 종료 전 수정하세요:'; printf '%s\n' "$out" | head -50; } 1>&2
exit 2
```

타입 검사가 실패하면 오류 앞부분 50줄을 돌려주고 `exit 2`로 턴 종료를 막습니다. Claude는 "다 했습니다"라고 말하기 전에 타입 오류부터 고쳐야 합니다. 둘째 줄은 루프 가드입니다. 이미 Stop 훅 때문에 다시 돌고 있는 중이면 그냥 끝내게 해서, 고칠 수 없는 오류 앞에서 끝없이 맴도는 일을 막았습니다.

권한 설정도 같은 쪽에 섰습니다. `.env` 파일과 `pnpm-lock.yaml`은 쓰지 못하게, 키와 시크릿 파일은 읽지도 못하게 막았고, `git push`와 `git reset --hard`는 매번 저에게 묻게 했습니다. 그리고 사람이든 에이전트든 커밋 전에는 `pnpm lint`와 `pnpm build`가 통과해야 합니다.

이렇게 놓고 보면 장치로 강제한 것은 모두 판단할 거리가 없는 것들입니다. 포맷, 타입, 비밀 파일. 어떤 컴포넌트를 어디에 둘지, 어떤 상태를 어디서 관리할지처럼 판단이 필요한 것은 문서로 남았습니다.

## 만드는 쪽과 검토하는 쪽을 나눴다

6월 27일, 규칙을 나누던 커밋에서 서브에이전트 네 개도 정의했습니다.

| 에이전트 | 맡는 일 |
| --- | --- |
| `frontend-builder` | UI와 기능 구현 |
| `bff-engineer` | MQTT와 SSE 사이의 브리지, Route Handler, 서버 전용 자격증명 |
| `code-reviewer` | 커밋 전 diff 검토 |
| `rules-keeper` | 규칙 문서와 인덱스 유지 |

이 중 `code-reviewer`만 성격이 다릅니다. 코드를 고칠 수 없는 읽기 전용 에이전트이고, 모델은 Opus로 고정했습니다. 지시문에는 "변경을 만든 사람과 다른 신선한 시각으로 diff만 보고 평가한다"고 적었습니다. 코드를 쓴 세션은 왜 그렇게 썼는지를 이미 알고 있어서, 그 맥락에 기대어 diff를 읽기 쉽습니다. 그래서 검토는 만든 맥락을 모르는 쪽에 맡기고, 고치는 일은 다시 메인 세션이 하게 나눴습니다.

`rules-keeper`를 따로 둔 것도 같은 맥락입니다. 규칙 문서도 코드처럼 낡습니다. 규칙이 흩어지거나 서로 어긋나면 그 규칙을 읽는 모든 에이전트가 함께 흔들립니다.

## 코드가 잊는 "왜"를 위키에 남겼다

규칙 문서는 "어디에 무엇이 있고 무엇을 지켜야 하는지"는 알려 주지만, "왜 이렇게 생겼는지"는 알려 주지 않습니다. Claude의 세션은 매번 새로 시작하고, 지난 결정의 이유는 여러 파일과 커밋 메시지에 흩어져 있습니다.

<!-- TODO: 9월 1일에 위키를 도입한 직접적인 계기가 있었는지. 예: Claude가 이미 한 번 고친 문제를 같은 방식으로 다시 망가뜨린 일, 결정 이유를 설명하느라 같은 말을 반복한 일 -->

9월 1일, 저장소 안에 `.wiki/`를 만들었습니다. Andrej Karpathy가 제안한 LLM Wiki 패턴을 코드 저장소에 옮긴 것입니다. 원래 패턴은 원자료(raw sources), 위키, 스키마의 세 층으로 나뉩니다. 여기서는 소스 코드와 규칙 문서가 원자료이고, `.wiki/` 안의 페이지가 위키, 위키 운영 규약을 적은 `SCHEMA.md`가 스키마입니다. 위키는 LLM이 쓰고 유지하며, 저는 읽고 방향을 정합니다.

가장 신경 쓴 것은 경계였습니다. 이미 규칙 문서가 있는데 위키가 같은 내용을 또 적으면, 둘 중 하나는 반드시 낡습니다. 그래서 API 계약과 파일 위치는 규칙 문서가 단일 출처이고, 위키는 그것을 복제하지 않고 링크만 하게 했습니다. 위키만의 영역은 여러 파일에 흩어져 있어 한 곳에서 읽을 수 없는 것들, 곧 아키텍처 종합, 개념, 실행 흐름, 그리고 비용을 치르고 확정한 결정입니다.

갱신 방식도 정했습니다. `/wiki-ingest`는 위키에 기록된 마지막 커밋부터 지금까지의 diff만 보고 영향받은 페이지만 고칩니다. 전체를 다시 훑지 않습니다. `/wiki-lint`는 위키를 믿고 큰 작업을 하기 전에 코드와 어긋난 곳이나 고아 페이지를 점검합니다. 위키를 읽을 때도 조건을 달았습니다. 위키 내용은 과거의 스냅샷이므로, 답하기 전에 페이지에 적힌 출처 코드로 다시 확인하게 했습니다.

마지막 커밋까지 위키 페이지는 15개, 위키만 고친 커밋은 42개가 쌓였습니다. 그중 하나가 `decisions/schema-drop-incidents.md`입니다. 외부 메시지를 zod로 엄격하게 검증하다 화면 전체가 조용히 멈춘 실제 장애 여섯 건과, 그 끝에 정한 "드롭보다 개방" 원칙이 날짜와 함께 적혀 있습니다. 코드에는 `optional()`과 기본값만 남지만, 이 페이지에는 왜 그 필드가 필수가 아닌지가 남습니다. 장애 이야기는 [3편](/blog/keeping-exhibition-screens-alive/)에 자세히 썼습니다.

## 이 글도 같은 방식으로 쓰고 있다

이 블로그도 같은 방식으로 만들고 있습니다. 저장소 루트의 `CLAUDE.md`에 글 작성 규칙을 두고, 경력과 프로젝트 자료는 저장소에 커밋하지 않는 로컬 위키(`wiki/`)에 출처와 함께 쌓습니다. 글을 고칠 때는 편집을 맡은 writer 에이전트를 따로 부릅니다. 그 에이전트의 첫 번째 금지 사항은 "사실을 지어내지 않는다"입니다. 이 글의 곳곳에 남아 있는 TODO가 그 규칙이 지켜진 흔적입니다.
