5월에 쓴 사전 설계 문서에서 태블릿 앱은 React Native였습니다. 그 문서를 쓴 사람은 저였습니다. 그런데 10월 전시장의 갤럭시 탭과 LG 스탠바이미, 삼성 TV에 떠 있던 것은 Next.js 웹앱 하나의 서로 다른 주소였습니다.

이 글은 [The Traveling Soul](/projects/the-traveling-soul/)의 전시 화면을 앱이 아닌 웹 하나로 만들기로 한 판단과, 그 결정 뒤에 풀어야 했던 문제들에 대한 이야기입니다. 웹앱이 하나면 그 뒤의 서버도 하나입니다. 이 글에서 다루는 문제는 대부분 거기서 나왔습니다.

## 내가 쓴 설계를 내가 바꿨다

웹 쪽 전체 아키텍처는 웹 개발을 맡은 세 명이 함께 논의해 정했습니다. 프런트엔드는 제가, 백엔드는 기아 임직원 한 분이, 미래차 관련 서비스는 다른 외부 크리에이터 한 분이 맡았습니다. 그중 전시 화면을 어떤 기술로 만들지는 프런트엔드의 몫이었고, 설계 문서에 적어 둔 React Native를 내려놓은 것도 제 판단이었습니다.

<Figure src={systemDesignRn} alt="사전 시스템 설계 문서의 3.5절 Tablet Application. 스택 항목에 React Native가 권장 1순위로 적혀 있고, 태블릿은 게이트웨이와 WSS로 연결된다고 되어 있다" caption="사전 시스템 설계 문서(SYSTEM_DESIGN) 3.5절. 태블릿 앱의 스택은 React Native였다" />

극적인 계기는 없었습니다. 판단의 중심은 두 가지였습니다.

- **필요한 기능은 이미 브라우저에 있었다.** 관람객이 말로 페르소나를 만드는 음성 입력은 마이크 녹음으로, 상태가 바뀌는 순간의 효과음은 Web Audio로, 현장 CCTV 실시간 영상은 WebRTC로, 움직이는 일러스트는 로티 애니메이션으로 풀 수 있었습니다. 앱으로 출시할 계획도 없었습니다. 웹 표준만으로 요구사항을 채울 수 있는데 React Native를 들여와 그 런타임과 아키텍처의 무게까지 떠안을 명분은 부족하다고 봤습니다.
- **화면 세 가지를 코드 한 벌로 다룰 수 있었다.** 5월 설계에도 태블릿만 있었던 것은 아닙니다. 체험에 참여하지 않는 바깥 관람객에게 참여자 현황을 보여 줄 스탠바이미 화면과, 시나리오 속 집에서 생긴 일을 띄울 TV 화면이 처음부터 계획에 있었습니다. 태블릿만 앱으로 만들면 이 두 화면은 따로 만들어야 하고, 같은 데이터를 다루는 코드가 두 벌이 됩니다. 웹 하나라면 데이터 처리와 상태 관리는 한 곳에 두고 화면만 주소별로 나누면 되니, 만들고 고칠 곳도 한 곳으로 줄어듭니다.

그 밖의 이점은 대부분 만들면서 알게 됐습니다. 아래 절들에서 하나씩 적습니다.

## 화면 셋, 서버 하나

결과적으로 앱 하나가 전시 화면 세 가지를 맡았습니다. 태블릿은 한 화면이 체험 단계에 따라 주소를 옮겨 갑니다. 첫 주소(`/`)의 인트로에서 페르소나를 만들고, 체험 내내 `/main`을 띄워 들고 다니다가, 모든 일이 끝나면 `/outro`의 하루 마무리 엔딩으로 넘어갑니다. 스탠바이미는 `/diorama`에서 참여자 현황을, TV는 `/tv`에서 집 이벤트 영상을 보여 줬습니다. 그리고 세 화면 뒤에는 Next.js 서버 하나가 있었습니다.

<Video src={tvEvent} poster={tvEventPoster} clip caption="TV의 /tv 화면. 평소에는 창밖 풍경을 띄워 두다가, 시나리오 속 집 현관에 방문객이 오면 방문객 알림 화면으로 넘어간다" />

기기마다 화면 크기와 비율이 달랐지만 반응형 레이아웃은 짜지 않았습니다. 그럴 이유가 없었습니다. 반응형은 같은 화면을 여러 크기의 기기에 띄울 때 필요한데, 태블릿은 갤럭시 탭 한 종류였습니다. 중간에 아이패드를 쓰는 안이 나온 적도 있지만 화면 비율이 맞지 않아 갤럭시 탭을 그대로 썼습니다. 기기가 정해져 있으니, 디자이너가 Figma에 그린 기준 해상도의 캔버스를 그대로 두고 실제 화면에 맞춰 통째로 키우거나 줄이면 충분했습니다.

방법은 루트 글자 크기 하나입니다. 기준 해상도에서 1px이 지금 화면에서 몇 px인지를 구하고, 루트 글자 크기를 그 16배로 둡니다. 그러면 1rem은 언제나 기준 해상도의 16px이 됩니다.

```css
:root {
  /* 기준 해상도의 1px이 지금 화면에서 차지하는 길이.
     가로·세로 비율 중 작은 쪽을 골라 캔버스가 화면을 벗어나지 않게 한다(contain-fit) */
  --z1-px: min(var(--z1-vw) / var(--z1-ref-w), var(--z1-vh) / var(--z1-ref-h));
}

html {
  /* 기준 해상도에서 1rem = 16px. 화면이 커지면 rem으로 적은 모든 치수가 함께 커진다 */
  font-size: calc(16 * var(--z1-px));
}
```

기준 해상도(`--z1-ref-w`, `--z1-ref-h`)는 화면마다 다릅니다. 스탠바이미 화면처럼 기준이 다른 페이지는 자기 기준 해상도를 선언하고, 루트 값만 그에 맞춰 바꿔 끼우게 했습니다. 해 보니 좋았던 점은 시안을 옮기는 일이 단순해졌다는 것입니다. Figma의 픽셀 값을 16으로 나눠 rem으로 적으면 글자, 여백, 아이콘, 모서리 반경이 한꺼번에 같은 비율로 따라옵니다. 컴포넌트는 Storybook에서 화면과 따로 떼어 확인했습니다.

## 브라우저와 로봇 사이의 다리

로봇, 카메라 인식, 서버는 MQTT라는 메시지 버스로 이야기를 주고받았습니다. 전시 화면도 이 버스에서 메시지를 받아야 했고, 관람객이 태블릿에서 무언가를 고르면 그 내용을 버스로 보내야 했습니다.

WebSocket을 쓰면 브라우저에서 버스에 직접 붙을 수도 있었습니다. 하지만 그러려면 버스 접속 보안키가 화면 코드에 들어가야 하고, 브라우저로 내려간 코드는 누구나 열어 볼 수 있습니다. 비공개 내부망에서 닷새 동안 열리는 전시이니 보안은 조금 가볍게 봐도 됐을지 모릅니다. 그래도 취약점을 알면서 남겨 두는 쪽은 택하지 않았습니다.

그래서 Next.js 서버가 대신 버스에 붙게 했습니다. 서버가 메시지를 구독해 형식을 검증하고 최근 상태를 기억해 두었다가, 브라우저에는 같은 출처의 실시간 스트림(SSE)으로 흘려 줍니다. 반대 방향도 같습니다. 태블릿이 보내는 요청은 서버의 API 라우트가 받아 검증한 뒤 대신 발행합니다. 보안키는 서버 환경 변수에만 있고, 브라우저는 자기 서버하고만 이야기합니다.

화면과 서버를 한 프로젝트에 담을 수 있는 Next.js였기에, 이 다리를 별도 서비스 없이 같은 앱 안에 놓을 수 있었습니다. 이것도 만들고 나서 알게 된 이점입니다. 다만 CCTV 실시간 영상은 예외로 두었습니다. 서버는 연결을 맺는 신호만 중계하고, 영상 자체는 브라우저와 영상 서버가 직접 주고받습니다.

<Figure src={architecture} alt="전시에서 쓴 구조. 다른 팀원 시스템과 메시지 버스(MQTT) 사이를 Next.js 서버가 구독과 발행으로 잇고, 태블릿·스탠바이미·TV에는 SSE로 전달한다. 태블릿의 요청은 POST로 서버에 들어간다. 아래에는 태블릿 앱이 게이트웨이를 거쳐 버스에 붙던 5월 설계 경로가 점선으로 그려져 있다" caption="버스 접속 보안키는 Next.js 서버에만 있고, 화면들은 자기 서버하고만 통신한다. 아래 점선은 5월 사전 설계의 경로" />

이 구조는 사전 설계의 원칙 하나를 비켜 갑니다. 5월 설계에서 태블릿은 게이트웨이를 거쳐서만 버스와 통신해야 했습니다. 그 원칙을 따르지 않은 이유는 두 가지였습니다. 게이트웨이를 따로 개발할 일정이 문제였고, 이 화면들이 쓰일 곳은 전시장 한 곳뿐이었습니다. 그래서 전시에 한해 게이트웨이라는 한 단계를 줄이고, 전시 화면 서버가 버스에 직접 붙는 쪽으로 정해졌습니다. 공개 서비스로 바꾼다면 게이트웨이를 거치는 구조로 되돌린다는 조건도 코드 옆 문서에 함께 적어 두었습니다.

## 서버가 하나라는 걸 잊은 전제

처음 서버를 만들 때는 태블릿 한 대가 곧 체험 하나라는 전제를 깔고 있었습니다. 그래서 서버가 기억하는 체험 상태도 한 벌뿐이었습니다.

그 전제는 9월에 깨졌습니다. 실제 로봇과 기기가 붙기 시작하고 여러 사람이 동시에 테스트하자, 한 태블릿에서 새 체험을 시작하면 다른 태블릿에서 진행 중이던 체험이 덮어써졌습니다. 전시장에서는 태블릿 여러 대와 스탠바이미, TV가 서버 하나를 같이 씁니다. 웹 하나, 서버 하나로 간 결정이 그대로 돌아온 셈입니다.

<Figure src={sessionSlots} alt="세션 구조 전후 비교. 9월 16일 이전에는 서버의 체험 상태 한 칸에 태블릿 A와 B가 함께 써서 B가 A를 덮어썼고, 이후에는 세션마다 슬롯을 따로 두고 스탠바이미와 TV는 짝 태블릿의 슬롯을 따라간다" caption="체험 상태 한 칸에서 세션별 슬롯으로" />

9월 16일, 관람객 한 명을 체험 하나로 보고 서버가 체험마다 슬롯을 따로 두도록 구조를 바꿨습니다. 메시지는 자기 세션 id로 슬롯을 찾아 그 체험에만 반영되고, 슬롯이 없는 세션의 메시지는 버립니다. 단일 상태 시절에는 이미 끝난 체험에 늦게 도착한 메시지가 다음 관람객의 상태를 덮어쓰기도 했는데, 그런 메시지도 이제 여기서 걸러집니다. 스탠바이미와 TV는 주소에 짝이 되는 태블릿을 지정해 그 체험을 따라가게 했습니다.

아래는 서버 코드에서 뼈대만 추린 것입니다.

```typescript
// 관람객(세션) 하나마다 슬롯 하나
interface SessionSlot {
  sessionUuid: string
  deviceInternalId: string | null // 이 세션을 연 태블릿
  lastActivityAt: number // 마지막 활동 시각. 유휴 만료 판정 기준
  // ...새로 붙은 화면에 다시 보내 줄 최근 상태들
}

interface Bus {
  sessions: Map<string, SessionSlot> // 키 = session_id
  // ...
}

// 세션 단위 메시지는 그 세션의 슬롯에만 반영한다
function forSession(handle: SessionHandler, { activity = true } = {}): TopicHandler {
  return (bus, payload, topic) => {
    const slot = bus.sessions.get(topicScope(topic))
    if (!slot) return // 슬롯이 없는 세션의 메시지는 버린다
    if (activity) touchSession(slot)
    handle(bus, slot, payload, topic)
  }
}
```

슬롯을 나누자 이번에는 언제 지울지가 문제였습니다. 전시장 태블릿은 관람객끼리 돌려 쓰기 때문에, 끝난 체험의 슬롯이 남아 있으면 다음 관람객이 앞사람의 데이터를 받을 수 있습니다. 그래서 같은 날 활동이 30분 동안 없는 슬롯을 정리하는 규칙을 넣었습니다.

이 규칙은 하루 만에 고쳐야 했습니다. 서버가 '활동'으로 세는 것은 메시지가 오가는 일뿐이라, 관람객이 한자리에서 화면만 들여다보는 동안에는 30분 내내 아무 메시지가 없을 수 있었습니다. 그대로 두면 쓰고 있는 체험을 서버가 끝내 버립니다. 9월 17일, 화면이 아직 연결되어 있는지로 기준을 나눴습니다. 연결이 끊긴 체험은 30분 뒤에 정리하고, 연결된 체험은 3시간을 상한으로 뒀습니다. 상한까지 둔 것은 스탠바이미와 TV가 늘 연결되어 있어서, 태블릿이 떠난 체험도 계속 살려 둘 수 있기 때문입니다.

```typescript
function sweepIdleSessions(bus: Bus): void {
  const now = Date.now()
  for (const slot of [...bus.sessions.values()]) {
    const connected = hasLiveListener(bus, slot) // 이 체험을 보고 있는 화면이 아직 연결되어 있나
    const ttl = connected ? SESSION_CONNECTED_TTL_MS : SESSION_IDLE_TTL_MS // 3시간 : 30분
    if (now - slot.lastActivityAt < ttl) continue
    expireSession(bus, slot, connected)
  }
}
```

## 브라우저만 있으면 된다는 말의 조건

웹을 고를 때 기댄 것은 브라우저였습니다. 필요한 기능이 브라우저에 다 있다는 판단은 맞았습니다. 그런데 전시장 기기들에 들어 있는 브라우저가 모두 같은 브라우저는 아니었습니다.

처음에는 스탠바이미의 내장 브라우저로 화면을 띄우려 했습니다. 반응이 너무 느렸고, 애니메이션이 느리게 재생됐고, 스타일 일부가 깨졌습니다. TV의 내장 브라우저도 비슷했습니다. 결국 두 화면 모두 윈도우 노트북을 연결해 노트북의 브라우저로 띄웠습니다.

느린 것은 기기 성능과도 얽혀 있어 원인을 하나로 짚기 어렵습니다. 스타일이 깨진 쪽은 구조로 설명할 수 있습니다. 같은 웹 페이지라도 태블릿에서는 크롬이, 스탠바이미에서는 webOS가 제공하는 브라우저가 띄웠습니다. 같은 앱이 태블릿의 크롬에서는 문제없이 돌았는데, webOS 브라우저의 엔진은 webOS 버전에 묶인 크로뮴입니다. LG가 공개한 표를 보면 webOS 22에는 크로뮴 87, 23에는 94, 24에는 108, 25에는 120이 들어 있습니다. 같은 크로뮴 계열이어도 몇 년 전 엔진이 그대로 돌고 있을 수 있다는 뜻입니다.

화면의 스타일은 Tailwind CSS v4로 썼고, Tailwind v4가 공식적으로 지원하는 가장 낮은 크롬은 111(2023년 3월)입니다. webOS 24 이하는 모두 이 기준에 못 미칩니다. 특히 webOS 23 이하(크로뮴 94 이하)라면 다음 두 가지가 겹칩니다.

- **`@layer`를 모르면 스타일이 통째로 빠진다.** `@layer`는 CSS 규칙을 층으로 묶어 우선순위를 정하는 문법으로, 크로뮴 99부터 지원합니다. 이 앱은 기본 스타일, 직접 만든 컴포넌트 클래스, Tailwind 유틸리티가 모두 `@layer` 안에 있습니다. 이 문법을 모르는 브라우저는 블록을 통째로 버리기 때문에, 바깥에 있던 CSS 변수와 키프레임만 남고 레이아웃과 컴포넌트 스타일이 빠집니다.
- **개별 변형 속성을 모르면 위치와 움직임이 어긋난다.** Tailwind v4는 요소를 옮기고 키우고 돌리는 유틸리티를 `translate:`, `scale:`, `rotate:`라는 개별 속성으로 내보냅니다. 크로뮴 104부터 지원하는 속성이라 그보다 낮은 엔진에서는 무시되고, 요소가 제자리를 벗어나거나 애니메이션의 움직임이 달라집니다.

반면 색을 섞는 `color-mix()`처럼 Tailwind가 대체 값을 함께 내보내는 기능은 상대적으로 덜 문제가 됩니다. 실제 화면이 이 중 어느 경우였는지는 전시에 쓴 스탠바이미의 webOS 버전을 알아야 단정할 수 있는데, 그 버전은 확인하지 못했습니다.

브라우저만 있으면 된다는 말에는, 그 브라우저가 지금의 표준을 안다면이라는 조건이 숨어 있었습니다.

배포에도 비슷한 단서가 붙었습니다. 웹이라 좋았던 점 하나는 서버 컨테이너 하나만 바꾸면 모든 화면이 새 버전을 받는다는 것이었습니다. 기기마다 새 빌드를 설치할 일이 없었습니다. 태블릿, 스탠바이미, TV용 PWA 설정을 따로 두어 홈 화면에서 앱처럼 띄울 수 있게도 했고, 몇 번은 그렇게 실행해 봤습니다. 하지만 전시 직전까지 수정이 이어져서, 실제 운영은 브라우저를 전체 화면으로 띄워 두고 새 버전이 나오면 새로고침하는 방식이었습니다.

문제는 스탠바이미와 TV처럼 하루 종일 켜 두는 화면이었습니다. 그런 화면은 아무도 새로고침해 주지 않습니다. 서버를 바꿔도 거기서는 옛 코드가 계속 돌았습니다. 이 문제를 어떻게 풀었는지는 [3편](/blog/keeping-exhibition-screens-alive/)에서 다룹니다.

## 다시 고른다면

다시 골라도 웹을 고르겠습니다. 이번에 막힌 곳은 웹이 아니라 기기에 딸린 내장 브라우저였고, 그 브라우저로는 지금 같은 화면을 만들기 어렵습니다. 다음에 같은 구성을 만든다면 웹이냐 앱이냐보다 먼저, 화면을 띄울 브라우저를 무엇으로 할지를 정해 두려고 합니다.
