5월에 쓴 사전 설계 문서에서 태블릿 앱은 React Native였습니다. 10월 전시장에 실제로 나간 것은 Next.js 웹앱 하나였습니다. 관람객이 손에 든 태블릿도, 바깥 관람객을 위한 스탠바이미도, 시나리오 속 집을 비추는 TV도 모두 같은 앱의 다른 주소를 띄우고 있었습니다.

이 글은 [The Traveling Soul](/projects/the-traveling-soul/)의 전시 화면을 왜 앱이 아니라 웹으로 만들었는지, 그리고 그렇게 만든 뒤 무엇을 새로 풀어야 했는지에 대한 이야기입니다.

## 다섯 화면은 누구를 보고 있었나

먼저 화면이 몇 개였고 누구를 위한 것이었는지부터 정리하면 이렇습니다.

- **태블릿 인트로**: 체험을 시작하며 나만의 페르소나를 만드는 화면. 음성으로 입력합니다
- **태블릿 메인**: 체험 내내 손에 드는, 유일하게 터치하는 화면. 대시보드, CCTV, 프로필, AI 대화가 모여 있습니다
- **태블릿 하루 마무리 엔딩**: 모든 일이 끝나면 영상처럼 자동으로 흘러간 뒤 체험을 마칩니다
- **스탠바이미 참여자 현황**: 체험에 참여하지 않는 바깥 관람객에게 지금 누가 어디서 무엇을 하는지 보여 줍니다. 터치는 없습니다
- **TV 집 이벤트 영상**: 시나리오 속 집에서 이벤트가 생기면 그 영상을 띄웁니다

전시 현장의 태블릿은 갤럭시 탭이었고, 스탠바이미는 LG, TV는 삼성 제품이었습니다.

다섯 중 둘은 애초에 태블릿이 아니었습니다. 태블릿 앱 하나로는 처음부터 다 담을 수 없는 구성이었던 셈입니다.

## 앱으로 낼 게 아니라면

React Native를 내려놓은 이유는 단순했습니다. 앱으로 출시할 계획이 없었고, 필요한 기능은 대부분 웹 브라우저만으로 충분했습니다. 요구사항을 웹 표준 기술로 모두 채울 수 있다면 React Native를 들여와 런타임과 아키텍처의 오버헤드를 떠안을 기술적 명분이 부족하다고 봤습니다.

{/* TODO: 아래 문단들의 근거(비태블릿 화면, 브라우저 API, 배포, PWA, 서버 동거, Figma 옮기기)는 코드에서 확인한 사실을 정리한 것. 이 중 당시 실제로 판단에 무게를 둔 것이 무엇이었는지 사용자 확인 필요. 아닌 것은 "해 보니 좋았던 점"으로 옮기기 */}

React Native로 갔다면 태블릿 앱과 별개로 스탠바이미와 TV를 위한 웹을 또 만들어야 했습니다. 웹이라면 코드베이스 하나에서 데이터 처리와 상태 관리 코드를 함께 쓰고, 화면마다 마크업만 따로 두면 됩니다.

필요한 기능도 이미 브라우저에 있었습니다. 음성 입력(마이크 녹음), 효과음(Web Audio), CCTV 실시간 영상(WebRTC), 로티 애니메이션 모두 브라우저 표준 API나 웹 라이브러리로 해결할 수 있었고, 네이티브 모듈이 꼭 필요한 기능은 없었습니다. 화면마다 PWA manifest를 따로 두어, 태블릿 홈 화면에 추가하면 주소창 없이 전체 화면 앱처럼 실행되게도 했습니다.

배포도 이유였습니다. 전시 직전까지 하루에도 여러 번 고쳐야 했는데, 앱이라면 기기마다 새 빌드를 설치해야 합니다. 웹은 서버 컨테이너 하나만 바꾸면 모든 화면에 반영됩니다.

마지막으로 Next.js는 화면과 서버(API 라우트)를 한 프로젝트에 담을 수 있습니다. 덕분에 아래에서 이야기할 MQTT 다리를 별도 서비스 없이 같은 앱 안에 놓을 수 있었습니다.

## 어느 화면에서도 시안 그대로

화면마다 크기와 비율이 달랐습니다. 화면별로 반응형 레이아웃을 따로 짜는 대신, 디자이너의 Figma 기준 해상도로 캔버스를 그리고 실제 화면에 맞게 통째로 확대·축소하는 방식을 택했습니다.

핵심은 루트 글자 크기입니다. 1rem이 늘 기준 해상도의 16px가 되도록 루트 글자 크기를 계산해 두면, Figma의 픽셀 값을 그대로 rem으로 옮겨 적어도 어떤 디스플레이에서든 시안의 비율이 유지됩니다. 웹 CSS에서는 이런 방식이 가장 자연스럽습니다. 컴포넌트는 Storybook에서 화면과 따로 떼어 확인했습니다.

## 브라우저는 MQTT에 붙을 수 없다

로봇, 카메라, 서버는 MQTT라는 메시지 버스로 이야기를 주고받았습니다. 그런데 브라우저는 MQTT에 직접 붙을 수 없고, 접속 정보를 화면 코드에 넣어 둘 수도 없었습니다.

그래서 Next.js 서버를 다리로 썼습니다. 서버가 메시지 버스를 대신 구독해 받은 메시지를 검증한 뒤, 브라우저에는 같은 출처의 실시간 스트림(SSE)으로 넘겨 줍니다. 반대 방향도 마찬가지로, 태블릿이 보내는 요청은 서버가 받아 검증한 뒤 대신 발행합니다. 접속 정보는 서버에만 있고, 브라우저는 자기 서버하고만 이야기합니다.

사전 설계에서는 별도의 게이트웨이를 거치는 구조였습니다. 이 원칙을 전시장 내부망 데모에 한해서만 완화해, 앱 서버가 메시지 버스에 직접 붙게 했습니다.

{/* 다이어그램 자리(선택): 로봇·카메라·서버 → 메시지 버스 → Next.js 서버(검증) → SSE → 태블릿·스탠바이미·TV, 그리고 태블릿 → POST → Next.js 서버 → 발행. 다른 팀원 시스템은 상자 하나로만 표시하고 내부 구조·토픽 이름은 넣지 않는다 */}

## "태블릿 한 대에 체험 하나"는 틀린 전제였다

처음 서버를 만들 때는 태블릿 한 대가 곧 체험 하나라는 전제를 깔고 있었습니다. 서버가 들고 있는 상태도 그 전제에 맞춰 짜여 있었습니다.

그런데 전시장에서는 여러 태블릿과 대형 화면이 서버 하나를 같이 씁니다. 9월 중순, 한 태블릿에서 새 체험을 시작하면 다른 태블릿에서 진행 중이던 체험을 덮어쓰는 문제가 드러났습니다. 결국 관람객 한 명을 체험 하나로 보고, 서버가 체험마다 상태를 따로 담도록 구조를 바꿨습니다. 스탠바이미와 TV는 짝이 되는 태블릿을 지정해 그 체험을 따라가게 했고, 활동이 끊긴 체험은 일정 시간이 지나면 정리되게 했습니다.
